# 灰度与验收

## 五期节奏

顺序不建议调换。每一期的目的不是“上更多功能”，而是“不把上一期挣来的信任花完”。

**第 0 期：归一化底座 + 契约，无 UI。**
上 `src/core` 与 `test`，跑通全部 fixture。这一期用户看不到任何东西，但它决定了后面四期的天花板。如果 `parseValue` 会猜错，后面所有规则都站不住。

**第 1 期：A1 的七条零歧义规则 + 封装回填。**
只上 `PHASE1_CODES`（R01 R02 R04 R05 R06 R12 R14）。这七条全部是“不可能报错”的类型：位号数与用量不等就是不等，同一位号被两行占用就是冲突。

目的只有一个：**让用户的第一印象是“它说的都对”。** 这个印象一旦建立，后面偶尔报错也会被当作意外；反之，第一印象是“又在胡说”，之后做得再准也没人看。

**第 2 期：A5 批量清理 + 三个建档入口。**
先做存量清理（不可见字符、描述污染、分类为空），再做新建预填。顺序很重要：存量脏的时候，新建预填会一直抽不准。

**第 3 期：A1 余下的规则 + A2 + A4 + 参数式搜索。**
这一期开始涉及判断力，medium 置信的建议会变多。监控采纳率，低于 30% 的规则直接下线。

建议把 A4 的字典审计安排在这一期的开头——它是一次性动作，第一次点下去大概率会发现存量错误，这种“当场拉出真问题”的体验对推广很有帮助。

**第 4 期：A3 + 版本发布门禁。**
门禁排最后，不是因为它难，而是因为它是一个**权力动作**。在用户还不信任规则的阶段就拿它卡发布，会直接引发反感，结果是运维被要求把整个功能关掉。

先让人信，再许它拦。

## 验收指标

**不要看调用量。** 调用量高只能证明入口好找，证明不了建议有用。看下面这几个。

| 指标 | 取数方式 | 红线 |
| --- | --- | --- |
| 单条规则采纳率 | `adoptionByCode()` | 低于 30% 的规则下线 |
| 空字段率下降 | 封装/分类/必填属性为空的比例 | 三个月内下降不足一半则重新评估方案 |
| 未关联零件行比例 | A1/R12 命中数 / 采购行数 | 这是采购链路的第一个断点，应当单调下降 |
| 体检到发布的返工次数 | 版本发布前被 block 拦住的次数 | 上升说明规则报得太晚，应提前到编辑时 |
| 建议被修改后接受的比例 | audit 里 `edited` / (`accepted` + `edited`) | 高于 40% 说明预填值系统性偏了 |

最后那一行很容易被忽略：用户总是“接受但改一下”，说明你的预填值方向对但系统性偷偏，这比直接报错更隐蔽。

## 灰度范围建议

第 1 期先开一个项目组，且选一个 BOM 比较脏的项目——脏才能看出价值。干净的 BOM 上跑体检，用户的感受是“这东西没用”。

每一期上线后留两周观察，先看 `dropped` 日志（Agent 自身 bug），再看采纳率。两周内 dropped 不为空就不要进下一期。

---

## 一个很容易走错的弯路

不要把五个 Agent 做成五个入口摆在菜单里。现有「AI 工具」菜单里的八张卡片已经证明了一件事：需要用户先想起“我要用 AI”、再去菜单里找到它、再把数据贴进去的工具，使用频率会很低。

判断挂载点对不对只需一个标准：用户本来就要点这个按钮吗？A1 新建版本前会点，A5 新建物料时会点，A3 开工单时会点。那就把能力长在那里，而不是再造一个入口。

A1 和 A5 上线之后，「AI 工具」菜单里至少三张卡片应该可以删了。**菜单里的入口变少，是这套方案成功的标志，不是失败的标志。**
